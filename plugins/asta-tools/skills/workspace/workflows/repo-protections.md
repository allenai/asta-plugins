# Workflow: recommended repo protections

None of these is required for the workspace to work. When you set up a GitHub repo, including Pages setup, recommend the ones that fit, ask the user, and apply only the ones they accept. The defaults ship as GitHub ruleset files in the skill's `assets/rulesets/` directory, released with each version:

| Ruleset | Recommend when |
|---|---|
| `default-branch.json` — blocks force-pushes and deletion of the default branch | Every repo. |
| `docs-checks.json` — requires the `docs / build` and `docs / paper-gate` checks | The repo has a paper or co-authors, `docs.yml` runs on every pull request targeting the default branch with no path filters, and the user accepts checking changes on a feature branch before updating the default branch (normally by merging a PR). Direct pushes without passing checks are rejected, including those by admins and bots unless an existing bypass applies. |

The docs checks are bound to the GitHub Actions app (`integration_id: 15368` on github.com), so a matching status from another source cannot satisfy them. When the project needs something different (another caller job name than `docs`, or a non-default branch), adapt a copy of the file rather than writing one from scratch. Confirm both check names and their app against a completed PR run at the project's selected workflow ref with `gh api --paginate repos/{owner}/{repo}/commits/<checked-sha>/check-runs --jq '.check_runs[] | {name, app: .app.slug, integration_id: .app.id}'`. On other hosts, pass `--hostname <host>` to every `gh api` command and replace both integration IDs in the copy with the observed GitHub Actions app ID; never remove the source binding to make a check match. If the checks have not run yet, defer this ruleset until they can be verified.

1. Before proposing required checks, inspect `docs.yml`: its `pull_request` event must cover the default branch without `paths`/`paths-ignore`, and run on `opened`, `synchronize` and `reopened` (the default event types also suffice). Check that caller-job conditions do not omit PRs, including drafts, and that both checks are reported at the selected workflow ref. A manual-only or filtered workflow needs a user-approved adjustment before its checks can be required.
2. Inspect all of the project's `.github/workflows/*.yml` and `*.yaml` files, following reusable-workflow calls at their selected refs. Each required context must identify only the intended docs job across these workflows; account for explicit job names, caller prefixes, matrix expansions and dynamic names. Check completed runs as well as the files: seeing a matching name once does not prove uniqueness. Resolve collisions with a user-approved job rename and update the contexts in the ruleset copy, or defer the docs ruleset if uniqueness cannot be established. [GitHub warns that duplicate job names can block merges](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches).
3. List existing rulesets with `gh api --paginate 'repos/{owner}/{repo}/rulesets?includes_parents=true'`; inspect applicable inherited rules and branch protections and explain overlap or conflicts to the user. Check whether the default branch uses a merge queue. If it does, `docs.yml` must also handle `merge_group` with `types: [checks_requested]` for that branch, and its caller and reusable workflow must report both required checks on the queue commit. Adding the event alone is unsafe: the shipped deploy job treats non-push events as PR previews. Use a user-approved adaptation of the caller and reusable workflow that skips deployment on `merge_group`, preserves PR previews and default-branch deploys, and still reports paper-build failures when deployment is skipped. Preserve the project's version policy; if its selected reusable workflow cannot do this, defer the docs ruleset until an accepted workflow change is merged and both contexts are verified on a queue run. [GitHub requires checks on merge groups](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#merge_group). Do not enable a merge queue by default.
4. Do not update an inherited ruleset through a repository endpoint or create a redundant one. For a same-named repository-owned ruleset, fetch it with `gh api repos/{owner}/{repo}/rulesets/<id>` and build an adapted payload from its writable fields (`name`, `target`, `enforcement`, `conditions`, `bypass_actors`, `rules`). Preserve unrelated rules, existing required checks and their sources, branch conditions, enforcement and bypass settings; add only the accepted protections. Do not replace it with the shipped JSON. If the existing settings conflict with the recommendation, explain the conflict and ask the user before changing them.
5. Show the proposed payload or diff and ask which protections the user accepts. For required checks, explain that unchecked direct pushes to the default branch will be rejected; if the user relies on them, defer this ruleset unless they accept changing that workflow. Do not add bypass actors by default. For an existing ruleset, make any removals or weakening explicit and require specific approval. Use that reviewed payload for the write.
6. Check admin access with `gh api repos/{owner}/{repo} --jq .permissions.admin`. With admin, create an accepted new ruleset using `gh api repos/{owner}/{repo}/rulesets -X POST --input <file>`, or update the existing one using `gh api repos/{owner}/{repo}/rulesets/<id> -X PUT --input <file>`. Otherwise give the user the appropriate one command and its payload file. Read the ruleset back after applying it and verify the accepted settings. Rulesets on private repos need a paid GitHub plan; if the API refuses, tell the user and move on.

Don't recommend these by default:

- Required approvals: whether to require review is the team's call.
- Required signed commits: each contributor's machine needs signing set up first.
- Protecting `gh-pages`: the workflow pushes to it, so protection breaks deploys.
