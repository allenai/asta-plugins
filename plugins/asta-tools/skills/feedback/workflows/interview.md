# Workflow: interview

Converse with the user about their experience using the Asta plugins, then write a narrative report at `<project-root>/.asta/feedback/<slug>/FEEDBACK.md` and stage any supporting files alongside it.

This workflow is conversational. Interview the user to get their general impressions and specific call-outs.

## Preconditions

None. Interview runs from any state, including mid-session.

## Output

A submission directory `<project-root>/.asta/feedback/<slug>/` containing:

- `FEEDBACK.md` — the narrative report (required; the CLI expects this exact name at the root).
- Zero or more supporting files the user chose to include.

`<project-root>` is the current working directory (or its git root, if it is a repo). `<slug>` is `<YYYY-MM-DD>-<short-kebab-topic>`.

## Steps

### 1. Orient

Compute once, before the conversation:

- `PROJECT_ROOT` = the git root of `pwd` if it is a repo, else `pwd`.
- Today's date (`date +%F`) for the slug and frontmatter.
- The Asta skills you actually invoked this session, from your own conversation memory (e.g. `find-literature`, `analyze-data`, `workspace`, `asta-flows`). You'll use these both to ask informed questions and to fill the report's `tools` field.

Skim recent work (`ls`, and `git log --oneline -10` if it's a repo) so you can reference concrete moments. Don't deep-dive.

### 2. Interview the user

Ask about their experience. Pick the prompts that fit — do not ask all of them, and follow the user's lead:

- What were you trying to do with Asta?
- What worked well? What felt slow, confusing, or wrong?
- Was there a moment where the agent did the wrong thing, or something you wanted it to do but couldn't?
- How did the result compare to what you expected?
- Anything you'd change?

Keep it short — one or two rounds is usually enough. If the user already stated their feedback, don't re-interrogate; just confirm you've captured it.

Then echo back a one-paragraph synthesis and a proposed short title, and get explicit confirmation before writing.

### 3. Offer to attach supporting material (optional)

Ask whether the user wants to include any agent-generated reports to support the feedback — e.g. a Quarto/HTML report from `workspace`, work item READMEs from `asta-assistant`, 
reports generated by `find-literature`. These are meant to illustrate agent failures and successes, not 
to reproduce the work it was doing.

- Do **not** stage input datasets, raw data, or large working files — they are not of interest here and the CLI will reject oversized bundles.
- Confirm each path with the user. If unsure whether a file belongs, ask rather than guessing.

Skip this step entirely if the user has nothing to attach — a narrative-only submission is perfectly valid.

### 4. Create the submission directory and write the report

```bash
SLUG="<YYYY-MM-DD>-<short-kebab-topic>"
DEST="$PROJECT_ROOT/.asta/feedback/$SLUG"
mkdir -p "$DEST"
```

Copy any confirmed supporting files into `$DEST` (preserve a readable name; small subdirectories are fine). Then write `$DEST/FEEDBACK.md` with this structure:

```markdown
---
title: <short title>
date: <YYYY-MM-DD>
tools: [<skills/plugins the feedback is about>]
sentiment: positive | mixed | negative
---

# <title>

## What I was doing
<1–2 paragraphs of context: the task, the goal.>

## What happened
<The narrative. What the user experienced, in their words, lightly edited. This is the core of the report — be concrete and specific.>

## What worked well
- <...>

## Friction and gaps
- <Where it was slow, confusing, wrong, or missing. Tie each point to a moment.>

## Suggestions
- <Concrete changes the user (or you) would make. Drop vague ones.>

## Supporting material
- `<filename>` — <one line on what it shows>   # omit this section if none
```

Write the user's perspective faithfully. You may add a short, clearly-labeled agent observation if it adds signal, but do not overwrite what the user said.

### 5. Confirm and offer submit

Show the user the directory path and the files in it (`ls -la "$DEST"`). Offer to run the **submit** workflow. Do not chain automatically — submission uploads the bundle and is user-visible.

## Out of scope

- Uploading anything. That is **submit**.
- Editing project files outside `$DEST`.
- Staging datasets or large working files.
